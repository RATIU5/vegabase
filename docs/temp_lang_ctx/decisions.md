# Decisions, open questions, prior art

Updated: 2026-11-18. IDs are never reused. Status: Decided, Proposed, Rejected, Open.

These IDs (D-1, Q-1, PA-1) are local to `docs/temp_lang_ctx/`. They are not the `D-001` / `Q-001` entries in `docs/core/DECISIONS.md`; those are cited as "core D-031".

## Decisions

All decided by the project lead on 2026-11-09.

**D-1 The existing draft is the candidate, not the truth** (closes Q-6). The end result of this process is a solidified spec. The draft in `docs/specs/` may be wrong in subtle or large ways. Assistant's reading, to be corrected if wrong: we start from the draft's constructs, and each one stays only if examples back it. Rejected: treating the draft as binding; ignoring it.

**D-2 Rendering runs in the core** (closes Q-1). Production traffic is rendered by the core's serve mode. The admin and template rendering for the admin run in the core's admin mode. The core is one server, deployed on edge or single-server compute. Consequence: stays out of the specs; no compile-to-another-target requirement.

**D-3 Data comes from many sources** (closes Q-2 in general; PoC choice is Q-12). A custom Stardust (temporal database) server holds pages, content and admin editor data. Third-party APIs supply other data. Consequence: the language can't assume one data source.

**D-4 Two files per component** (closes Q-4). Each component has a template file and a schema/data file. Rejected: one combined file per section. Follow-ups: Q-13, and the word "data" here bears on Q-9.

**D-5 Plugins connect data sources and add field schemas; no filters** (closed Q-5 and Q-8). **Superseded by D-6 the same day.** Rejected: plugin filters.

**D-6 Plugins only define data sources** (supersedes D-5; closes Q-5 and Q-8). A plugin defines data sources and transforms data on its way to and from the template. To the template: through `use` statements. From the template: through forms and JS fetch. Plugins do not define or control schemas. Rejected: plugin filters; plugin field schemas. Consequences: no plugin code is callable from a template expression; the PoC plugin is a data source. Not yet confirmed: what a `use` statement looks like and where it lives (Q-9). How plugin data gets a type was settled by D-8. **Superseded by D-64 on 2026-11-17.**

Draft features that D-6 rules out for plugins (assistant's reading of the consequence; each is in `docs/specs/` today):

| Draft feature | Where | Under D-6 |
| --- | --- | --- |
| Plugin-declared components, record types for editors, aliases, unions | VEGS §8 | Out. A plugin ships only the read-only shape of its data (D-8) |
| Plugin directives on fields (`@acme.swatch`) | VEGS §4.5, §11 | Out |
| Plugin `fn` in `@show` and `@validate(check = ...)` | VEGS §7.3, §7.4 | Out |
| Plugin `loader` in `@validate(check = ...)` (`acme.slugFree`) | VEGS §7.4 | Unclear: it is a data source, but used for validation, not for a template |
| Plugin page kinds | VEGS §8, core Q-046 | Out |
| Plugin `loader` backing a `data` field | VEGS-DATA §1, §2 | Kept. This is the data source |
| Plugin `action` (writes from forms and fetch) | VEGS §4.4 | Kept by D-6; v0.1 scope is Q-16 |

Whether the Shopify vendor lib counts as a plugin here is Q-18.

**D-7 One construct: the component** (closes Q-3). A component may or may not have a slot. "Section" and "block" are not keywords. Rejected: separate `section` and `block` declarations, because a slotless page-level component and a nested block with a slot fit neither. Consequence: where a component may be placed is stated by the slot that accepts it.

**D-8 The plugin ships the shape of its data** (closes Q-15; narrows D-6). A plugin defines which data sources a theme can `use`, in a template and in a schema. The plugin author exports the data shape, "Zod-like", alongside the plugin. The theme author never writes it. Rejected: theme-authored shapes; untyped plugin data. D-6's "no schemas" still holds for editor field types and component schemas. Not yet confirmed: the authoring form of the export (Q-17), and what `use` means inside a schema (Q-9). **Changed by D-64 on 2026-11-17:** a plugin writes its shapes in `.vega` files and may define more than shapes.

**D-9 Every file that needs data from a system has a `use` statement** (lead, 2026-11-10; answers part of Q-9). Any file, schema or template, that needs data from any system, core or third party, names that system with `use`. Why: maximum type safety and traceability. Confirmed by the lead: (b) a component's own editor fields need no `use`; (c) the data need itself (source and arguments) sits on the schema field, as in E-1. (a) settled on 2026-11-10 (closes Q-21): there is no exception for received data, because the reader needs the type information. Assistant's reading of the lead's "No, it needs type information": a file that reads a value typed by a system has `use` for that system, however the value arrived. Consequence if (a) holds: the draft's implicit own-namespace `@global` fields and its "unused `use`" warning change meaning.

**D-10 Template delimiter is `{{ }}`** (lead, 2026-11-10; closes Q-19). One delimiter for output, tags and the header. Rejected: single braces as in the draft, which clash with literal braces in JSON-LD, inline CSS and JS.

**D-11 Template header is one block: `declare Name`, then `use` lines** (lead, 2026-11-10; closes Q-20). The file starts with one `{{ ... }}` block holding one statement per line. `declare ProductHero` states that this file is the template of `ProductHero`. Rejected: separate `{{use}}` and `{{type}}` tags; the keyword `type`. Assistant's objection, overruled: `declare` can read as creating the type, which the schema file does. Assistant's reading, not yet confirmed: the block is required, appears once and comes first; `declare` is its first line.

**D-12 A parent can pass data to the components in its slot, and the child's schema types it** (lead, 2026-11-10; closes Q-22). A value passed to slot children has its type declared in the receiving component's schema. Rejected: untyped passing ("the slot just has the data"). Supersedes the draft rule that slot children are fully opaque. Syntax is not decided: Q-23. Sketch: E-2.

**D-13 No pages in code** (lead, 2026-11-11). Pages are defined only in the admin. Code defines plugins, locales and components (`.vegs`, `.vegt`, js, css), plus one root settings file (TOML or `.vegs`, not chosen). Folders carry no meaning. Removes from the sketch: `@page`, `@not_found`, `@route`, `@query`, `url(page = ...)`. Not decided: how a component gets the data the URL names (Q-34), links to entity pages, the `<html>` shell, the not-found page.

**D-14 No commas in lists** (lead, 2026-11-12). One item per line; the newline separates items. **Amended by D-45 on 2026-11-16:** entries that share a line need a comma.

**D-15 Borrow selected parts of DUST; do not adopt its syntax** (lead, 2026-11-12; research: PA-16). Rejected: a fully DUST-like syntax. Borrowed, form still a sketch until the lead confirms the rewritten Hero and ProductInfo: (1) `/` for namespaces and `.` for fields (`use <std theme>`, `std/Image`); (2) newline-separated lists (D-14); (3) field constraints in one `{ }` block in place of `@x(...)` chains; (4) `slot` as a type wrapper with `min`/`max`; (5) page data as a host constant such as `:route/handle` (candidate for Q-34). Not borrowed: truthiness, `is ... as` narrowing. Changed by the lead, 2026-11-12: item (3) is dropped, directives keep the `@` prefix; `use` is one line per library with no angle brackets (`use std`), not `use <std theme>`. The lead also wants Odin to stay an influence. Changed again by the lead, 2026-11-12: item (1) is reverted for types, components, groups and globals, which use `.` (`std.Image`, `theme.sections`); "slash may be used for the `std/empty` or something". Assistant's reading, not confirmed: functions keep `/` (`std/empty`, `shopify/money`, loaders such as `shopify/productBy`). Assistant's objection: two separators for one namespace strains "one obvious way"; with `.` everywhere a function is still recognisable by its `( )` or its place after a pipe.

**D-16 One file type, `.vega`; a component may be one file or split** (lead, 2026-11-12; closes Q-36; changes D-4 and the brief line on separate languages). A file may hold schema code, a template, or both. Assistant's objection, overruled: allowing both forms gives two ways to write a component and keeps the pairing rule (and `declare`, D-11) alive for the split form. Not decided: how schema code is marked off from HTML (Q-38).

**D-17 `{{ }}` wraps all code that is not HTML, as a block or inline** (lead, 2026-11-12; extends D-10; closes the first part of Q-38). A `.vega` file is HTML by default. Schema and data code, tags and output all sit inside `{{ }}`. Rejected: `---` lines for the schema block, because they do not work inline. Assistant's concern, answered by a proposed rule (not confirmed): schema code contains `{ }`, so the parser counts braces, and the `}}` that closes a multi-line block stands alone on its line, which keeps a missing-brace error on that line. Added by the lead, 2026-11-12: declarations (`use`, types, components, fields) appear only in the first block of the file; later `{{ }}` hold tags and output.

**D-18 `.` is the only name separator** (lead, 2026-11-12; replaces item (1) of D-15). `std.Image`, `std.empty(...)`, `shopify.money`, `theme.sections`. No `/` in names. Assistant's reading, not confirmed: page constants follow, `:route.handle`.

**D-19 Any code inside `{{ }}` must work and make sense both inline and in a block** (lead, 2026-11-12). First consequence, from the lead: a directive on the line above a component declaration is out. Other consequences are proposals: Q-44.

**D-20 A component's directives go inside its body** (lead, 2026-11-12; closes Q-44 item 1). Reason from the lead: ten directives after the word `component` are hard to read. Rejected: after the kind, before `{`. Assistant's proposed rule, not confirmed: they come before the first field; a directive after a field belongs to that field. This is token order, not line position, so it passes D-19.

**D-21 There is an output keyword, `out` or `print`** (lead, 2026-11-12). A statement inside a `{{ }}` block that writes a value into the final HTML at the block's position. Not decided: the name, and whether `{{x}}` stays as a short form (Q-45). Lead, later on 2026-11-12: the short form stays, and a value standing alone as a statement is written to the document, in any block. Assistant's point: this makes the keyword redundant. **Final, lead, 2026-11-12: `out` is dropped** (closes Q-45). The rule: a statement is a declaration, a tag or a value, and a value is output, escaped for its position, never as markup.

**D-22 A directive is admin metadata only; constraints are type arguments** (lead, 2026-11-12; closes Q-37 and items 1 and 2 of Q-47). Directives: `@label`, `@hint`, `@show`. Test: deleting every directive changes neither the stored data nor the HTML. Constraints: `Text(max = 160)?`, `Int(min = 0, max = 90)`, `slot(theme.Button, max = 2)`, `Text(pattern = "...")`. Assistant's choices while applying it, not confirmed: lists are `List(T, min = 1, max = 12)` (replaces the `[]T` assumption); metadata follows the default (`Int(min = 0, max = 90) = 40 @show(...)`); the custom message of the old `@validate` has no home yet.

**D-23 A template names its component's values with one single-colon line** (lead, 2026-11-12; closes Q-48 and Q-23 part 3; replaces `declare` from D-11). `hero: theme.Hero`, then `{{hero.heading}}`. Single colon because it is a value of that type that exists only at render time; `::` is for what is fully known up front (the Odin rule, checked against the Odin overview). No `self` keyword, no `declare`. The same line connects a split template to its schema. Rejected: reading fields by full path through `theme`; `card :: current(...)`. Assistant's rules, not confirmed: a file with HTML has exactly one such line; a component has exactly one template in the theme; the name is the author's choice. New cost seen in the theme: the name can match a translation key prefix, `{{hero.heading}}` beside `t(hero.label)` (Q-42). **Changed by D-59 on 2026-11-16:** the naming line is removed; a template reads fields and props by bare name.

**D-24 Names the theme declares are written bare and are visible from every file** (lead, 2026-11-12). No `theme.` prefix and no `use theme`. Reason from the lead: `theme` was used in every file. A prefix therefore always means a library (`std.`, `shopify.`); no prefix means "declared in this theme" or built in. Condition from the lead: "as long as it doesn't cause recursive uses"; which cycles are errors is Q-49. In D-23 the line is now `hero: Hero`. Assistant's choices while applying it, not confirmed: declaring the same name twice, or a built-in name, is an error naming both places; group names are capitalised like types (`Blocks`).

**D-25 Cycles between theme names** (lead, 2026-11-12; closes Q-49). Errors: an alias cycle; a record that contains itself directly, not through `List` or `?`; a `render` cycle. Allowed: a slot that accepts its own component, because stored content is finite. Declaration order and file order never matter.

**D-26 `|` is both the union and the pipe** (lead, 2026-11-12; closes Q-47 item 5). Position tells them apart: a union sits in a type, a pipe in a value. No `|>`. The lead wrote "use | for union and type"; the assistant reads "type" as "pipe".

**D-27 `@show` stays; no `if` around fields** (lead, 2026-11-12; closes Q-46 and Q-47 item 6). Every field is always stored, so a condition never changes the stored shape. `if` is for HTML, values and attributes inside a tag. `use` and declarations never sit inside `if`.

**D-28 The language never names the CMS, only a host** (lead, 2026-11-12; closes Q-50). Everything from outside a file arrives through three host-supplied things: field values, loaders (`data ... = lib.fn()`), page constants (`:route.x`). The CMS is one host; a script with sample data is another. Directives are ignorable by any host (D-22). Rules out any keyword that only makes sense with an admin.

**D-29 A group is a named union; there is no `group` construct** (lead, 2026-11-12; closes Q-47 item 3). `Blocks :: Title | Price | BuyButton`, used as `slot(Blocks, min = 1, max = 12)`. Removes the `:: group` declaration and the `group` line in each component. Costs accepted: a new component must be added to the list by hand; a component no slot accepts goes unnoticed unless a check warns (proposed, not confirmed).

**D-30 The language works with and without a CMS, including as a plain server-side template language** (lead, 2026-11-12; extends D-28). A host program passes field values, loaders and page constants and receives HTML. How a host embeds the renderer is a runtime matter and stays out of the specs (brief).

**D-31 A page's root is a shell component with `head` and `body` slots; metadata is an ordinary component in `head`** (lead, 2026-11-12; closes Q-51 and Q-40). No new construct. Condition from the lead: a per-page override, else the site-wide value. Met with existing constructs: (1) the `head` slot has default content (`= [ SiteMeta {} ]`), which a page replaces with its own metadata component; (2) inside the component, nullable editor fields override, and `??` falls back to page data and then to site-wide settings (`meta.image ?? meta.post.image ?? Site.settings.shareImage`). Rests on unconfirmed pieces: `:route.handle` (Q-34), the `Site` global and site-wide settings (Q-27), pipe binding looser than `??` (Q-43). Sketch: `example-theme-vega/layout/Shell.vega`, `SiteMeta.vega`, `ArticleMeta.vega`.

**D-32 A component gets the data the URL names through a page constant, `:route.handle`** (lead, 2026-11-12; closes Q-34). `product: data shopify.Product = shopify.productBy(handle = :route.handle)`. The data need stays on the schema field (D-9 c). Page constants are host-supplied (D-28). Assistant's rules, not confirmed: the constant takes the type of the loader parameter it is passed to; a host refuses to render (the admin refuses to place) a component on a page that does not supply the constant; `:query.page` works the same way for query-string values (Q-26) but a query value can be absent, so it needs a default.

**D-33 A pipe mixed with another operator needs parentheses** (lead, 2026-11-12; closes Q-43). `(a ?? b ?? c) | std.imageUrl(width = 1200)`. No precedence rule to remember. A pipe alone needs none: `image | std.imageUrl(width = 800)`. `x | std.length > 0` is an error; write `not std.empty(x)` or `(x | std.length) > 0`.

**Example sets, 2026-11-12.** Current: `examples/` (six `.vega` files, the set to show stakeholders). `example-theme/` and `example-theme-vega/` were deleted on the lead's instruction; entries above that cite files in them refer to sketches that no longer exist. `examples.md` holds only a stale fragment. Not covered by the six files: `render`, `yields`, the split form, `Ref`, `List`.

**D-34 Translation keys are strings** (lead, 2026-11-12; closes Q-42). `t("hero.label")`, not `t(hero.label)`, so a key cannot be mistaken for a field. A key missing from a locale table is still a check-time error.

**D-35 No `global` construct** (lead, 2026-11-12: "global doesn't seem as necessary"; the assistant agrees). A component that needs site-wide data declares it like any other data need: `site: data std.SiteSettings = std.siteSettings()`, read as `shell.site.locale`. Every name a template reads is then declared in its own file. The host runs a loader once per distinct call (D-31), so repeating the line costs no extra fetch. Cost: the line is repeated in each component that needs it. Still open: where theme-wide editor settings live (Q-27).

**D-36 The words `data`, `given` and `locale` stay** (lead, 2026-11-12). `data`: the field is filled by a loader. `given`: the field is passed in by the parent, through a slot or `render` (also closes Q-23 part 1 and Q-25). `locale`: a table of translations for one language.

**D-37 The type decides escaping; there is no `raw`** (lead, 2026-11-12; closes Q-7). Every value is escaped for its position (text, attribute, URL). Only a `std.RichText` value is output as HTML, and only between tags. A template cannot turn `Text` into HTML. Whoever produces a `RichText` cleans it: the host on save, or the library that loads it. The type is the brief's "explicit opt-out". Known limit: the language cannot check that a library's `RichText` is clean.

**D-38 A loader that finds nothing: the field's type decides what happens** (lead, 2026-11-16). `product: data shopify.Product = ...` finds nothing: the host stops and renders the site's not-found page with status 404; that page is an ordinary admin page (D-13). `product: data shopify.Product? = ...` finds nothing: the value is `null`, and the template must handle it with `if` or `??`. A template never sets a status and never redirects; redirects stay in the host and the admin. The lead first asked whether the template should answer a 404 with a redirect; the assistant objected that a template is pure and cannot set a status after HTML has started; the lead agreed.

**D-39 A comment starts with `#` inside `{{ }}`** (lead, 2026-11-16: "Comments use `{{# ... }}`"). The comment runs to the end of the line or to `}}`, whichever comes first, so it works in a block and inline (D-19; the block form is the assistant's addition, accepted by the lead). A comment outputs nothing. A literal `{{` in the output is written as a string, `{{"{{"}}`; no new construct. Not decided: how a comment holds the characters `}}`.

**D-40 No whitespace syntax** (lead, 2026-11-16). Rejected: Liquid's `-` markers. Rejected: always removing whitespace, because the space in `{{first}} {{last}}` and everything inside `<pre>` is content. Rules: (1) a line that holds only a tag or a comment leaves nothing behind, not even its newline; (2) whitespace inside an HTML start tag is normalised by the compiler, so `<option value="x" >` is output as `<option value="x">`; (3) all other whitespace is kept as written.

**D-41 `std.asset` takes a literal path; link fields have the type `std.Url`** (lead, 2026-11-16; closes the asset half of Q-31, the form target stays open). `std.asset(path = "theme.css")`: the path is a literal, and the check fails if the file does not exist. `std.Url` allows `http`, `https`, `mailto`, `tel` and relative paths; anything else is rejected on save. A `std.Url` is escaped for its position like any other value (D-37).

**D-42 Equal loader calls run once per render** (lead, 2026-11-16). Two fields that call the same loader with equal arguments, in one component or in several, cause one request. The engine reads every data need before rendering and supplies the result to each field that asked.

**D-43 Function arguments are passed by position only** (lead, 2026-11-16). `std.take(info.galleryLimit)`, not `std.take(count = info.galleryLimit)`; `std.imageUrl(1200, 630)`. Applied to every library function call in the six examples. Not yet decided, so left as written: the names in type arguments (`Text(max = 80)`, `Int(min = 0, max = 90)`, `slot(Blocks, min = 1, max = 12)`) and in the values a parent passes to a slot (`{{slot info.blocks(product = info.product)}}`).

**D-44 A type's limits go in a `{ }` block after the type** (lead, 2026-11-16; replaces the type-argument form in D-22 and settles the first open point of D-43). `Text { max = 80 }`, `Int { min = 0, max = 90 } = 40`, `Text { max = 160 }?`, `slot(Blocks) { min = 1, max = 12 }`. The order on a field line is: type, limits, `?`, default, directives. One rule for the language: parentheses take values by position, braces take `name = value`. Rejected: all positional, `Int(0, 90)`, with a linter showing the names, because `Text(80)` does not say minimum or maximum and a diff shows no hints. Assistant's adjustment, accepted with the rewrite: a pattern is a string, `pattern = "^[a-z-]+$"`, not a new literal between backslashes. Still open: the names in the values a parent passes to a slot, `{{slot info.blocks(product = info.product)}}`.

**D-45 Entries are separated by a comma or a newline** (lead, 2026-11-16; amends D-14; replaces the assistant's proposal under D-19 that any whitespace separates). Entries that share a line need a comma between them. Entries on separate lines need none; a comma at a line end is allowed. Covers every `{ }` and `[ ]` list and the arguments in `( )`. Consequence: a newline has meaning inside braces, so a value breaks across lines only inside parentheses. Assistant's proposal, not confirmed: the formatter removes commas at line ends.

**D-46 Admin settings sit in one `@{ }` block** (lead, 2026-11-16; changes the form in D-22, keeps its meaning). `subheading: Text { max = 160 }? @{ label = "Subheading" }`. The block holds `name = value` entries (`label`, `hint`, `show`) and follows D-45, so it is written on one line or across several. A field reads as two blocks: the type with its limits, then the admin block. A component's own block sits inside its body before the first field (D-20). Everything that starts with `@` is for the admin editor and nothing else is; deleting every `@{ }` block changes neither the stored data nor the HTML. Reason from the lead: three or more `@x()` calls on one type, with more to come. Rejected: keeping `@label("X")` as a short form, because it gives two spellings.

**D-47 A lowercase name with `( )` is a function call; a capitalised name with `{ }` is a type being filled in** (lead, 2026-11-16). `( )` holds bare values by position (D-43) and order matters. `{ }` holds `name = value` entries and order does not matter. A `name =` never appears inside `( )`. Types start with a capital letter and every other name starts lowercase; the checker enforces it. `[ ]` stays for lists of values (lead: "Keep [ ]"). Words: `Text { max = 160 }` is a limited type and the block is its limits; `BuyButton { text = "Buy" }` is a component value and the block is its fields; any `{ }` of `name = value` entries is a field block. Still open: slot passing, `{{slot info.blocks(product = info.product)}}`, which has names inside parentheses (the lead leans to braces); and `List(shopify.Variant)`, a capitalised name with parentheses.

**D-48 `slot` is a word in front of the type, like `data` and `given`** (lead, 2026-11-16; changes the form in D-44). `blocks: slot Blocks { min = 1, max = 12 } = [ BuyButton {} ]`, `head: slot HeadParts { max = 1 }`. Replaces `slot(Blocks) { ... }`, which put a type inside parentheses.

**D-49 A parent passes values to a slot in a field block** (lead, 2026-11-16: "Yes, braces"; closes the first open point of D-47; changes the form in D-12 and D-23's example). `{{slot info.blocks { product = info.product } }}`. A slot that passes nothing stays `{{slot shell.head}}`. It matches a component value, `BuyButton {}`, which also sets fields in braces. The formatter writes a space before the closing `}}`; the parser counts braces (D-17), so `}}}` also parses. `render` takes the same form, `{{render ProductCard { product = item } }}` (lead, 2026-11-16: "Yes, same form").

**D-50 The list type is `List { of = T }`** (lead, 2026-11-16; closes the last open point of D-47; replaces the unconfirmed `List(T, min = 1, max = 12)` noted under D-22). `List { of = shopify.Variant }`, `List { of = Text, min = 1, max = 12 }`. The item type and the limits share one field block, so no capitalised name is followed by parentheses anywhere in the language. Assistant's recommendation, overruled: keep `List(T)` as a stated exception, because `of` puts a type among limits.

**D-51 Schema and props are separate** (lead, 2026-11-16; changes D-36: the words `data` and `given` are removed; extends D-23). Inside `component { }` is the schema: fields and slots, stored by the host and shown in the admin. Outside it, in the first block, each other single-colon line is a prop: a value the template receives at render. The admin never knows a prop exists. Three forms: `product: shopify.Product` (a parent must pass it); `product: shopify.Product = $shopify.product` (a parent may pass it, else the page supplies it, D-52); `site: std.SiteSettings = std.siteSettings()` (the engine loads it). A prop is read by its bare name, `{{product.title}}`; stored values keep their name, `{{buy.text}}`. `@{ }` blocks, limits and pickers appear only in the schema. Reason from the lead: developers pass values to child components, and that must never be reflected in the admin.

**D-52 A page value is written with `$`, and a plugin declares which kind of page supplies it** (lead, 2026-11-16; changes D-32: `:route.handle` becomes `$route.handle`; the lead chose this over a loader call with the URL handle and over making the page the outermost parent). `product: shopify.Product = $shopify.product`. Reason for `$`: a second `:` on the line was confusing. The theme never sees the key: the shopify plugin declares a page kind, such as a product page, with its URL shape and the values it supplies, and resolves the product from the URL. Known limit: the type of a page value is checked from code, but whether a given page supplies it is checked by the host at placement, as in D-32. Not designed yet: how a plugin declares a page kind.

**D-53 A loader may read a prop or a schema field** (lead, 2026-11-16). `similar: List { of = shopify.Product } = shopify.recommendations(product)`. The engine orders the fetches. A loop between loaders is an error.

**D-54 A value passed to a slot flows down to every block inside it** (lead, 2026-11-16; closes Q-30; extends D-12). Components between the one that passes and the one that receives write nothing. The nearest passed value wins. Fully checked from code: for every component with a prop that must be passed, every chain of slots that can reach it, through the unions, must contain a slot line that passes that name with a matching type. Cost accepted: a layout block allows the same children wherever it sits, so product sections need their own union and layout block. Rejected: forwarding by hand with a `pass` keyword, which has the same cost and more lines.

**D-55 A schema field with a library type is a picker** (lead, 2026-11-16: "Product should always be a product picker"). `product: shopify.Product @{ label = "Product" }`. The admin shows the plugin's picker, the host stores the reference (an id), and the engine supplies the full value at render. A list of picks is `List { of = shopify.Product, max = 4 }`. **Amended 2026-11-17 (lead approved the fix; wording is the assistant's):** this covers a library type that names a stored thing, such as `std.Image` or `shopify.Product`. `std.Url` is a plain input checked on save (D-41), not a picker.

**D-56 A plugin's shape carries names, types and a one-line description for everything it offers** (lead, 2026-11-16; extends D-8). Reason from the lead: an author should not need a plugin's docs open; the code editor lists what `shopify.` and `$shopify.` offer, with argument names shown while typing. Positional arguments (D-43) depend on this.

**D-57 Props sit in a `props { }` block beside the component** (lead, 2026-11-16; changes the placement in D-51, keeps D-23). `props { info: ProductInfo, product: shopify.Product = $shopify.product }`, one entry per line in practice. The line that names the stored values, `info: ProductInfo`, sits in the same block, so templates still read `info.galleryLimit` and `product.title`. Reason from the lead: bare `name: Type` lines at the top level looked like values, against D-21. Assistant's recommendation, overruled: a `props { }` block inside the component with bare names for both fields and props. Rejected: a `prop` word on each line; `export`. Not solved: nothing but position ties the block to its component. **Superseded by D-59 the same day.**

**D-58 `part` defines a code-only component** (lead, 2026-11-16). `ProductCard :: part { product: shopify.Product }`. Its body holds props directly and it has no schema, so it needs no `props { }` block and its props are read by bare name. A part cannot be listed in a union, so the admin never offers it. `render` calls a part or a component: `{{render ProductCard { product = item } }}`. The word is the lead's request for something shorter than "snippet"; `part` is the assistant's choice, accepted. **Superseded by D-59 the same day.**

**D-59 One keyword, `component`, with a `fields { }` block and a `props { }` block** (lead, 2026-11-16; supersedes D-57 and D-58; changes D-23; keeps the separation of D-51). `fields { }` holds what an editor fills in: fields, slots, pickers, limits and `@{ }` blocks; the host stores it and the admin shows it. `props { }` holds what code passes or loads; the admin never sees it. Both blocks are optional. The component's own `@{ }` block is the first line inside `fields`. A template reads fields and props by bare name, `{{heading}}`, `{{product.title}}`, `{{slot blocks}}`; a field and a prop with the same name is an error. There is no `part`: the admin offers a component only if a union used by a slot lists it, and a component in no union, such as `ProductCard`, is code-only. A component with no fields that a union lists, such as a divider, is still offered. Not solved: how a template in a separate file (D-16) names its component, now that the naming line is gone.

**D-60 A component's own `@{ }` block sits at the root of `component { }`, outside `fields`** (lead, 2026-11-16; changes one sentence of D-59; replaces the placement in D-20). `Hero :: component { @{ label = ... } fields { ... } }`. It describes the component, not a field, and a component with no fields still needs a label. It stays `@{ }`, so everything that starts with `@` is for the admin (D-46). Rejected: a keyword such as `admin { }`, which would give admin settings two spellings. `@{ }` on a single field stays after that field's type. Assistant's proposal, not confirmed: a warning for an admin block on a component that no union lists.

**D-61 A template names its component with `template Name`** (lead, 2026-11-16; solves the open point of D-59 and the split-file case of D-16). `template Hero` in the first block says that the HTML in this file is the template of `Hero`, and makes its fields and props readable by bare name. The component may be defined in the same file or in another. Rejected: `use Hero` (the lead's first idea), because `use` already names a library (D-9). Errors before rendering: HTML in a file with no `template` line; two `template` lines in one file; two files that supply a template for one component. The line is always required in a file that has HTML, also when the component is defined in the same file (lead, 2026-11-16; the assistant had recommended leaving it out there). A file with no HTML, such as a shared file of unions, aliases and locales, has no `template` line; a `template` line in a file with no HTML is an error.

**D-62 A parent may loop over the children of a slot** (lead, 2026-11-17; changes D-12 and D-54, which let a parent pass values down but not see its children). `{{for panel in panels}} ... {{slot panel}} ... {{/for}}`. `{{slot panels}}` stays as the short form that outputs every child with no wrapper. Conditions from the lead: reasonable limits, not confusing for editors or developers, and it must work with a Datastar, hypermedia approach. Limits, accepted by the lead on 2026-11-18: (1) a slot allows only `for`, `std.empty` and `std.length`, so code never hides what an editor placed; (2) every child is output exactly once (lead, 2026-11-18: "Yes, exactly once"; reason in D-65): the template uses the short form once, or exactly one loop over the slot holds one `{{slot child}}` with no `if` between the `for` and it. Another loop over the same slot may read fields but not output, as the tab bar in `Tabs.vega` does, and an `if` around the whole loop is allowed, as in `Grid.vega`; (3) a parent reads fields only, never props, and only fields that every component in the slot's union has with the same type; (4) no branching on which component a child is. Not designed: how a URL asks the host for one component alone. The id of a placed component is D-65.

**D-63 There is a content type** (lead, 2026-11-17: "Yes we need a content type. Maybe the content keyword?"). A content type is the shape of a thing an editor creates many of and does not place on a page: a blog post, a recipe, an event. Condition from the lead: it follows the same rules and format as everything else. Form, accepted by the lead on 2026-11-18: the keyword is `content`, and `Recipe :: content { @{ label = "Recipe" } fields { ... } }` has the shape of a component with no `props` and no template. A field of that type is a picker, as in D-55 (lead, 2026-11-18: "Yes, a picker"): `recipe: Recipe @{ label = "Recipe" }`. A theme may declare a content type, as a plugin may (lead, 2026-11-18: "Yes, themes can"); this changes the last sentence of core D-029, which says entity types come only from `std` or extensions. Assistant's reading, not confirmed: the core stores a theme's entries and is their type owner (GLOSSARY: Type owner names an extension today). Examples: `Recipe.vega`; `RecipeCard.vega`, which takes a `Recipe` as a prop; `FeaturedRecipe.vega`, which has the picker field. Not decided: what a picker field that is not `?` holds after its entry is deleted; how a component loads one entry or a list of entries; the name of the page value for an entry; whether a content type may hold a slot; a plain field group with no entries of its own, such as a nav link.

**D-64 A plugin may ship anything a `.vega` file can hold, and more** (lead, 2026-11-17: "Plugins can define .vega files"; "a plugin can do anything you can do in a vega file, and load it via the plugin, and plugins can do even more too"; supersedes D-6 and the "theme author never writes it, plugin author exports the shape" form of D-8). A plugin may define components, unions, aliases, content types and locales in `.vega` files. Consequences, assistant's reading: the rows marked "Out" in the table under D-6 no longer hold; the authoring form of a plugin's data shape is `.vega` (closes Q-17). Accepted by the lead on 2026-11-18 ("Yes, prefix + opt-in"): in a theme, a plugin's names keep their prefix (D-18), and the admin offers a plugin component only when a theme union lists it, `Sections :: Hero | maps.Map`. Example: `Map.vega` and the `Sections` line in `shared.vega`. Assistant's reading while writing the example, not confirmed: inside its own files a plugin writes its own names bare, `Map :: component`, as a theme does (D-24). Not decided: how a `.vega` file is tied to its plugin. "More" means four things (lead, 2026-11-18: "Yes, those four"): loaders, page kinds (D-52), pure functions such as `shopify.money`, and form actions. Consequences, assistant's reading: template functions come from core and from plugins (closes Q-14); the Shopify library is a plugin like any other, with no separate tier (closes Q-18); D-6's "no plugin code is callable from a template expression" no longer holds for pure functions. Not decided: how a plugin declares each of the four; whether form actions are in v0.1 (Q-16) and how a template names one (Q-31). Assistant's proposal, not confirmed: a theme cannot replace a plugin component's template. Not decided: whether one plugin may `use` another.

**D-65 A template reads the id of its own placed component as `$id`** (lead, 2026-11-18: "yes, $id, but not child.id"; settles the first "not designed" point of D-62). `<section id="{{$id}}">`. The host supplies it, like every `$` value (D-28, D-52); it is a `Text` that is unique on the page and safe as an HTML id. Rejected by the lead: `child.id` for a parent to read a child's id. Accepted by the lead on 2026-11-18: every child of a slot is output exactly once, because a child output twice would write the same `$id` twice (now D-62 limit 2). Assistant's proposed alternative, not confirmed: there is no way to read another component's id. A parent owns the wrapper it writes around a child, so it builds that wrapper's id from its own id and the position, `id="{{$id}}-{{i}}"`, and the child uses `$id` inside its own template. Reasons: `child.id` would collide with a field named `id`, and D-62 limit 3 says a parent reads fields only. Cost: a wrapper id built from the position changes when an editor reorders the children. Assistant's proposals, not confirmed: `$id` is the same on every render of the same placed component; a component output by `render` gets an id derived from its parent's id and its position; Wider meaning of `$`, assistant's reading: a value the host supplies, not only a value the page supplies.

**D-66 A vendor lib is a plugin that the core team maintains as first-party** (lead, 2026-11-18: "a vendor lib is a plugin, just maintained as first-party by the core team"; confirms the reading in D-64 that closed Q-18). The language has one kind of extension. `shopify` is a plugin; what sets it apart is who maintains it, not what it may declare. Core D-015 still holds: one vendor lib per commerce platform. Not decided, and the core docs say otherwise today: whether a first-party plugin still runs as signed native code while other plugins run in WASM (core D-007); whether a pure function from a plugin that is not first-party may run while a page renders (core D-028 says template functions come only from the core or vendor libs, with no WASM on the render path). Assistant's recommendation, not confirmed: keep both runtime rules as they are and treat them as a host matter, so the language states one rule and the host decides where each plugin's code runs. **Settled by D-67.**

**D-67 First-party plugins run as native code; every other plugin runs in WASM** (lead, 2026-11-18: "agree, keep plugins as wasm and lib as native"; settles the two open points of D-66; keeps core D-007). The contract is the same for both: the `.vega` files plus the declared loaders, kinds of page, functions and actions. The host loads a first-party plugin as signed native code and any other plugin in the sandbox. Assistant's reading of "agree", to be corrected if wrong, since the lead answered a recommendation with four parts: (1) a plugin may `use` a first-party plugin, and the admin refuses to enable it unless that plugin is enabled (closes the open point of D-64); (2) dependencies point one way: a first-party plugin never depends on another plugin, and in the first edition no plugin depends on a plugin that is not first-party; (3) a plugin's own code calls a first-party plugin through host imports, checked against its approved capabilities, as `core/DESIGN.md` §6 already says; (4) no WASM runs while a page renders, so only the core and first-party plugins supply functions a template calls (keeps core D-028; narrows the "pure functions" of D-64 to first-party plugins). Point (4) confirmed by the lead on 2026-11-18 ("Yes, correct"); points (1) to (3) remain the assistant's reading. A plugin that is not first-party still ships components, content types, locales, loaders, kinds of page and form actions.

Status of every row: Proposed (assistant's notes, not yet confirmed by the lead).

### Template language

| ID | Source | Borrow | Avoid | Why |
| --- | --- | --- | --- | --- |
| PA-1 | Liquid | Sections and blocks as the mental model; pipe filters read left to right | Undefined renders as empty string; untyped auto-injected globals; `assign`/`capture` mutation; two delimiter kinds plus `-` whitespace markers; schema JSON embedded in the template | It is the baseline. Every "avoid" is a failure a type checker removes, which is the PoC claim |
| PA-2 | Go `html/template` | Contextual escaping decided by where the output sits in the HTML | The `.` cursor that changes meaning inside blocks; errors only at render time | Escaping by context is checkable; a moving implicit subject strains "explicit over implicit" |
| PA-3 | Svelte, Astro, JSX | One brace form `{expr}`; typed props; components with slots | Script blocks, reactivity, arbitrary host-language expressions | Authors know the shape; the host-language escape hatch breaks the power budget |
| PA-4 | Handlebars, Mustache | Logic-less discipline: logic lives outside the template | Untyped helpers as the escape hatch; `{{{ }}}` making unescaped output one keystroke away | Shows where logic leaks once the core is small: into helpers nobody can check |
| PA-5 | Jinja, Twig | Block tags with named closers | Macros (user-defined functions), template inheritance, `set` | Each is outside the power budget; inheritance also hides where markup comes from |

Also noted: Elm and Rust compiler messages as the bar for error quality (file, line, field, expected vs found, one suggested fix). Askama and Templ as proof that compile-time-checked templates are practical.

### Schema language

| ID | Source | Borrow | Avoid | Why |
| --- | --- | --- | --- | --- |
| PA-6 | Shopify section schema | Setting type maps to an editor input; blocks with limits; presets | JSON inside the template file; string ids nothing checks; no reuse between sections; settings untyped where the template reads them | It proves editors can live on generated UI. Its failures are all missing types |
| PA-7 | GraphQL SDL | Field lines `name: Type`; named types; lists | Nullable by default; directives as the catch-all for every new feature | Non-null by default removes most missing-data bugs. Directive sprawl hides structure in decoration |
| PA-8 | Prisma schema | One readable line per field; constraints as attributes; precise errors | Mixing storage and relation mechanics into the shape | Closest in feel to "shape plus simple constraints" |
| PA-9 | Sanity, Contentful | References between content; field-level validation; field groups for the editor | Schemas written as code with validation callbacks | Code schemas can't be statically checked and can't generate a form without running them |
| PA-10 | JSON Schema, CUE, Zod | Constraints as data (`min`, `max`, `pattern`, enum) | JSON Schema's verbosity and combinators (`anyOf`, `not`); CUE's unification; Zod's code | Constraint power grows into a logic language quickly; the brief caps it at "simple constraints" |

PA-16 DUST (https://guide.stardustdb.com/DUST.html, read 2026-11-12 by a research agent: about 75% of the language chapters, a quarter of the page). A Lisp-like, expression-oriented language over RON (no commas, no colons, newline-separated). Borrow: registry-path imports with `/` names, newline lists, constraints as data, host-bound `:name` constants, the four escape contexts (html-text, html-attribute, url-query-value, url-form-field). Avoid: runtime-only contracts, truthiness, in-place mutation, recursion and macros, open shapes, canonical key sorting (loses field order). It has no templating, slots, components or editor metadata.

Also noted: Protobuf's schema-evolution discipline (renames and removals against stored content) as a later concern, not v0.1.

### Observations on the existing draft (`docs/specs/`)

Proposed, pending Q-6. Each is a strain against the brief, not a verdict.
